# Domain events are ID-only facts on a topic exchange, best-effort unless a consumer cannot afford to lose them

Legnaris publishes domain events to RabbitMQ so that asynchronous consumers can react to facts without the API calling them. The first consumers are analytics (LGN-188), email, and the cleanup after account deletion (LGN-190). An event reports a fact that already happened. It can trigger an effect for the user, such as an email, but no domain rule depends on it arriving: state always lives in MongoDB (for example `users.plan`, ADR 0009). Payloads carry IDs, changed keys and metadata, never Sheet values or PII. Most events are published best-effort from the API. The few that a consumer cannot afford to lose go through the `event_outbox` introduced in ADR 0009. Decided in LGN-173.

## Considered Options

- **Event sourcing:** rejected in `docs/TDD.md`. It brings no product need, and on standalone MongoDB the event write cannot share a transaction with the entity write.
- **Transactional outbox for every event:** on standalone MongoDB the outbox row is a second write without a transaction anyway, so it does not fully close the gap. It adds a Mongo write to every autosave in exchange for analytics precision we do not need.
- **Pending events embedded in the entity document:** a single-document write is atomic, but every repository would have to manage events, and `sheet.deleted` has no document left to live in.
- **Synchronous publish with confirms in the request:** up to 5 s of extra latency on every autosave while the broker is slow.
- **Values in the payload:** a consumer storing events would become a second copy of player data under LGPD. A consumer that needs values reads them from the API.
- **One event per field, or semantic events (`sheet.level_up`):** no consumer needs them yet. They can be added later as new types.
- **Pseudonymizing `actor_id` with an HMAC:** it needs key management and only pays off with an external consumer. Every consumer is ours.

## Decisions

- **Events are facts, jobs are not events:**
  - `generation.<kind>.requested` is a job for the worker. It stays on the `generation` exchange with the publish and sweeper rules from ADR 0007, outside this catalog.
  - The facts that result from a job (`generation.succeeded`, `generation.failed`, `generation.accepted`) are events.
- **Naming:** `<aggregate>.<past_tense_verb>`, lower snake case inside each part (`sheet.updated`, `user.deleted`).
- **Versioning:** an integer `version` in the envelope, starting at 1. It never goes into the type or the routing key. A change that only adds fields keeps the version. Renaming, removing or changing the meaning of a field bumps it.
- **Envelope:**

  ```json
  {
    "id": "<uuidv7>",
    "type": "sheet.updated",
    "version": 1,
    "occurred_at": "2026-11-13T12:00:00Z",
    "actor_id": "<user uuid, or null when the system acts>",
    "aggregate": {"type": "sheet", "id": "<uuid>"},
    "data": {"changed_keys": ["hp", "dice"], "sheet_version": 42}
  }
  ```

  - `id` is generated by `idgen`. It is also the AMQP `MessageId` and the consumers' deduplication key.
  - Decoders tolerate unknown fields, so the contract may only grow within a version (same rule as the email envelope).
  - Messages are `application/json` and persistent.
- **Payload privacy:**
  - `data` carries IDs, changed keys and metadata only. It never carries Sheet values, generation concepts or output (ADR 0008), email, username or any other PII.
  - `actor_id` is the user's UUID in clear. It is still personal data under LGPD, so **every consumer that stores events must handle `user.deleted`** by deleting or anonymizing that user's events.
- **Delivery tiers:**
  - **best-effort** (default):
    - The service hands the event to an in-process publisher after the write succeeds. The publisher uses a buffered channel, one goroutine and publisher confirms.
    - The request never waits for the broker and never fails because of it.
    - When the broker is down or the buffer is full, the event is dropped, logged, and counted in `legnaris_events_dropped_total{type}`.
  - **guaranteed:**
    - The service writes the entity first and then inserts the event into `event_outbox` (ADR 0009, same claim/lease pattern as `email_outbox`). There is no transaction.
    - The relay publishes it with confirms, retries with backoff, and marks it `failed` after the attempt cap.
    - Delivery is at-least-once once the row exists. A crash between the entity write and the outbox insert can still lose the event.
  - The tier is part of each event's catalog entry. Moving an event from best-effort to guaranteed is not a contract change.
- **API connects to the broker:** best-effort events mean the API now holds an AMQP connection, as ADR 0007 already required for generation jobs. EML-16 ("the app never depends on the broker") no longer holds. The API still starts and serves requests while the broker is down.
- **Ordering and duplicates:** there is no ordering guarantee, not even within one aggregate, and duplicates can happen. Consumers deduplicate by `id`. When order matters, they use the version fields in `data` (for example `sheet_version`).
- **Topology:**
  - A new durable **topic** exchange `legnaris.events`, separate from `legnaris.email` and `generation`. The routing key is the event `type`.
  - Each consumer declares and owns its queue and dead-letter queue (for example `analytics.events` and `analytics.events.dead`) and binds the patterns it needs (`sheet.#`, `#`).
  - The API and the relay only publish to the exchange and know no queues. A consumer adds the tiered retry queues from the email pipeline only if it needs them.
- **Catalog v1:**

  | Type | Aggregate | `data` | Tier | Emitted |
  |---|---|---|---|---|
  | `sheet.created` | sheet | `template_id` | best-effort | today |
  | `sheet.updated` | sheet | `changed_keys`, `sheet_version` | best-effort | today |
  | `sheet.deleted` | sheet | — | best-effort | today |
  | `sheet.imported` | sheet | `template_id` | best-effort | with Sheet import |
  | `generation.succeeded` | generation | `kind` | best-effort | with generation (ADR 0007) |
  | `generation.failed` | generation | `kind`, `error_code` | best-effort | with generation |
  | `generation.accepted` | generation | `kind`, `sheet_id` | best-effort | with generation |
  | `user.registered` | user | — | best-effort | with this ADR's implementation |
  | `plan.changed` | user | `from`, `to` | guaranteed | with billing (ADR 0009) |
  | `user.deleted` | user | — | guaranteed | with account deletion (LGN-190) |

  - One `sheet.updated` per successful save, including layout and dice writes (`changed_keys: ["layout"]`). `changed_keys` lists top-level Sheet data keys plus `layout`, `dice` or `name`. Layout writes do not bump `sheet_version`.
  - Campaign, NPC and Monster events come later. Each one is added to this catalog, with its schema and tier, by the card that introduces the aggregate.
  - **Campaign events** are defined in ADR 0011 (LGN-179): six best-effort `campaign.*` facts plus `campaign.deletion_requested`, which is guaranteed because the asynchronous deletion depends on it.

## Consequences

- **Implementation is split into follow-up cards**, sequenced by LGN-181:
  - An `events.Publisher` port in the services, like the existing Observer ports, plus the best-effort AMQP adapter and the `legnaris.events` topology.
  - Emitting the three `sheet.*` events.
  - Every later event ships with the feature that produces it.
- **ADR 0009** already introduces `event_outbox` and the relay loop for `plan.changed`. `user.deleted` reuses them.
- **LGN-190** must emit `user.deleted` through the outbox. **LGN-188** must handle `user.deleted` in the analytics store.
- **Analytics precision:** dropped best-effort events show up in `legnaris_events_dropped_total`. Dashboards built on events are approximate by design.
- **Tests:**
  - Envelope golden file and tolerant decoding.
  - The publisher drops and counts when the buffer is full or the broker is down, and the request still succeeds.
  - A failed entity write emits nothing.
  - `changed_keys` for data, layout and dice saves.
  - No Sheet value or PII appears in any payload.
  - Topology declaration is idempotent.
