# AGENTS.md — backend/internal/sheet/template (DAG, Registry, Templates)

## Key Concepts

- **Template** — code-defined structure (fields, formulas, deps). Immutable by ID (`fantasy_v1`, `fantasy_v2`...).
- **DAG** — compiled dependency graph with topological order. Built once at boot per template and immutable afterwards:
  - Private (never embedded) mutex
  - Single read-lock acquisition per `Recalculate` and per `ValidateUpdateKeys`
  - `GetNode` returns value copies
- **Sheet** — `map[string]any` document linked to a template. Base fields editable; derived fields computed.
- **Recalculation** — `DAG.Recalculate(original, updates)` returns only changed derived fields (cascading).

## Gotchas

- **Templates are code, not DB** — no `template` collection in Mongo; templates live in the in-memory registry
- **DAG keys are flat path keys** (`stats.dexterity`) while engine env uses underscores (`stats_dexterity`) — field names validated at `BuildDAG` (LGN-52): every segment must match `^[A-Za-z][A-Za-z0-9]*$`, so neither `.` nor `_` can appear in a name and the two key encodings can never collide (regression tests: `TestBuildDAG_FieldNameValidation` and LGN-41 case in `TestBuildDag_EdgeCases`)
- **Updates are validated by the DAG itself** — the sheet service flattens the PATCH payload and calls `DAG.NormalizeAndRecalculate` (LGN-105), whose `validateEditableLocked` core runs the LGN-66 rule: unknown key or group prefix → `UnknownFieldError` (400 `UNKNOWN_FIELD`), derived field → `NotEditableError` (400 `INVALID_REQUEST`). The exported `ValidateUpdateKeys` wrapper keeps the same rule for callers that validate without recalculating (unit tests). Editability is deliberately *not* enforced inside `Recalculate`, because `Create` seeds a sheet with every field, derived ones included
- **Exclusive groups are enforced in one locked pass** — `DAG.NormalizeAndRecalculate` (LGN-105) validates editability, collapses each touched `exclusive_group` to at most one non-zero member and recalculates under a *single* read-lock acquisition; the service uses it instead of calling `ValidateUpdateKeys` + `NormalizeExclusiveUpdates` + `Recalculate` (three acquisitions). Members must be numeric 0/1 proxies: a non-numeric value → `ExclusiveValueTypeError` (400), two members on → `ExclusiveGroupConflictError` (400), a member turned off leaves siblings unchanged. `Recalculate` keeps serving `Create`; `ValidateUpdateKeys`/`NormalizeExclusiveUpdates` stay public for callers that validate or normalize without recalculating (unit tests today) and delegate to lock-free cores
- **Nesting depth is capped** — `maputils.FlattenPathKeys`/`ToEngineEnv` reject a map deeper than `maputils.MaxNestingDepth` (5) with `ErrMaxDepthExceeded`, which the service maps to 400 `INVALID_REQUEST`. The flatten walk is recursive over user-controlled PATCH data, so the cap stops a deeply nested body from exhausting the goroutine stack (DoS). Templates nest at most three levels (root → group → leaf), leaving headroom
- **Template IDs are slugs** — `FetchTemplate` rejects anything outside `^[a-z][a-z0-9_]*$` with `ErrTemplateIDInvalid` *before* the registry lookup (LGN-86 follow-up), so junk gets 400 instead of 404 on `GET /templates/:id`; the sheet service calls `FetchTemplate` first in `Create` and translates the typed error itself, so `POST /sheets` behaves the same
- **Registry and DAGs are frozen after boot** — `Registry.List()`/`FetchByID()` return deep copies (registry clones `DefaultTemplates()` on ingest), DAGs resolved per ID via `Registry.DAG(id)` through `sheet.DAGProvider` interface (no `DAGs()` map accessor), and `DAG` guards state with unexported mutex: never acquire twice — read through `HasNode`/`GetNode`/`GetChildren`/`ValidateUpdateKeys` (each takes the lock itself), or stay under single lock `Recalculate` takes (recursive RLock deadlocks with queued writer, regression test `TestRecalculate_ValidationRunsUnderSingleReadLock`)
- **PATCH body** uses nested map (`{"data":{"stats":{"dexterity":12}}}`), flattened internally to DAG dot-keys
- **Change detection (LGN-59)** — `Recalculate` only cascades the keys `changedUpdates` says really changed, compared with `maputils.Equal`'s *relative* epsilon (1e-9): rounding/type coercion cannot start a cascade, but the absolute slack grows with magnitude (up to 1.0 at 1e9) and integers above 2⁵³ collapse in `float64`, so `Equal` is unsuitable for fields needing exact large values (currency, XP). A PATCH whose values are unchanged returns `{}` and recomputes nothing: stale derived values do not self-heal on a no-op update.
- **`config` vs `rules`** — `config.*` leaves are 0/1 wiring flags: the desktop renders any first path segment `config` as a toggle, so non-flag numbers must not live there. Tuning numbers (ability modifier base/step, passive base, spell save base) live in `rules` and are read by the generated formulas, so retuning a system never edits formula text.
- **Seed by type** — `FieldSchema.SeedValue()` (`text → ""`, `bool → false`, otherwise `Default`) is what `Create` stores through `buildNestedAllFields`. The JSON `default` key stays numeric for every type (clients decode it as `num`), so a text field showing `default: 0` in the DTO is expected, not a bug.
- **Formulas and `DependsOn` must match exactly** — `BuildDAG` checks that declared deps exist, but not that every identifier a formula reads is declared: an undeclared read evaluates against the compile env's `0.0` instead of cascading. `TestFantasyV1_FormulaReferencesMatchDependsOn` enforces both directions; text leaves never carry formulas (the compile env is numeric).
- **Section order is declared, not sorted** — `Template.SectionOrder` lists top-level keys in display order and `TemplateDTO.MarshalJSON` emits `fields` that way, because `encoding/json` would sort the map alphabetically and the desktop renders sections exactly as they arrive (identity and the table numbers first, rules/config last; fantasy_v1 runs identity, combat, derived, attacks, stats, modifiers, saves, skills, spells, rules, config). Changing a template's `SectionOrder` is presentation only: a Sheet's stored `section_order` and `pinned` are keyed by name, so they keep resolving (`TestValidateLayout_FantasyV1_StoredLayoutSurvivesSectionReorder`). Ghost or duplicate entries are skipped, unlisted keys and orderless templates fall back to alphabetical, and nested groups always stay alphabetical.
- **Row keys mirror the web `buildRows`** — `SectionRowKeys` lists a Template's Rows per Section and is the only definition the backend has of a valid Layout key: lone leaf → dotted path (`stats.dexterity`); group whose `Columns` resolve to at least one leaf leaf child → one table Row keyed by the group path (`skills.acrobatics`; its columns and any exclusive members under it are *not* Rows); leaves sharing a non-empty `exclusive_group` within a Section collapse into one Row `<parentPath of first member>#<exclusive_group>` (`config#armorClassAbility`) — a single-member group stays a lone leaf. Children walk alphabetically, sections follow `SectionOrder`, a Section with no leaf is omitted. Change `buildRows` and this function together (`web/src/engine/field_grouping.ts`)
- **`ValidateLayout` takes plain lists** — `(Template, sectionOrder, pinned)` so this package needn't know `sheet.Layout`; it returns `UnknownLayoutSectionError`, `UnknownLayoutRowError` or `DuplicateLayoutKeyError`, which the sheet service maps to 400 `INVALID_REQUEST`. The suggested-pin errors are boot-time only and never reach a client.
- **`SuggestedPins` are template-authored, strict and read-only** (ADR 0002) — `Template.SuggestedPins` is an ordered list of Row keys (same grammar as Layout `pinned`) the client may offer as a player's first Pins; it ships as `suggested_pins` on the template DTO, omitted when empty, and is never written into a Sheet or its Layout. `ValidateSuggestedPins` runs in `BuildRegistry` (boot), so a bad template stops the API from starting: a key that is not a Row of any Section (unknown path, table column, exclusive member, bare Section) → `UnknownSuggestedPinError`, a repeat → `DuplicateSuggestedPinError`, more than `MaxSuggestedPins` (6, the web vitals strip capacity) → `TooManySuggestedPinsError`. Unlike a player's Layout this is code reviewed in a PR, so it is never tolerant. Keep the cap in sync with the web strip; `cloneTemplate` and `ToDTO` copy the slice, and fantasy_v1's entries must stay lone number leaves (`TestFantasyV1_SuggestedPins`)
- **Dice defaults are template-authored, strict and read-only** (ADR 0005) — `Template.SectionDice` (Section key → expression) and `Template.RowDice` (Row key → expression) hold the default Dice expressions; they ship as `dice: {section, row}` on the template DTO (the whole block omitted when both maps are empty, an empty side omitted too) and are never written into a Sheet. `ValidateDiceDefaults` runs in `BuildRegistry` (boot) on top of `backend/internal/dice`: a key that is not a Section (or Row — same `SectionRowKeys` grammar as Layout pins) → `UnknownDiceSectionError` (`UnknownDiceRowError`); a refused expression, a Row default whose `@`/path is not a numeric Field, or a Section default that fits none of its Rows → `InvalidDiceError`, which wraps the `*dice.Error` (`errors.Is(err, dice.ErrNonNumericField)`, `dice.ClassOf`). Sections are checked before Rows, keys alphabetically, so the reported error is stable. A Section default only has to fit *one* Row (`dice.ValidateSection`), and a table Row such as `skills.acrobatics` needs `@.<column>` because the Row key itself is not a Field. `cloneTemplate` and `ToDTO` copy both maps; `attacks.*.damage` (free text) is not a Dice default. fantasy_v1's seed is pinned by `TestFantasyV1_DiceDefaults`

## Template Errors

- Declare own typed errors (sentinels or custom types) — **do NOT import `apperr`**
- Wrap with `fmt.Errorf("...: %w", err)`
- Service layer translates to `apperr` at boundary
- `ErrTemplateIDNotProvided` (missing template ID, LGN-66) and `ErrTemplateIDInvalid` (malformed slug, LGN-86 follow-up) are translated to 400s at the boundary: `backend/internal/app.templateError` handles the `/templates` routes and the sheet service's `translateTemplateErr` handles `POST /sheets` — the same boundary translation `backend/shared/json` decoding errors get
